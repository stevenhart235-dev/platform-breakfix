# EKS Milestone 23: AWS-native lifecycle-status semantics discovery

## Scope and accepted baseline

M23 is read-only and design-only at platform baseline `8cba79a271bb22a9bd3a3ecf5fe456e8b431c618`. The pinned foundation remains signed `v0.2.0` commit `d042fa4e9a3b8ef975554fa56b7c9a4b61547e54`. No executable EKS status producer is added, and `get_lab_status -Provider eks` remains `PROVIDER_UNSUPPORTED`.

The target remains an AWS-native producer feeding the existing exact neutral shape `{State, CreatedAt, ExpiresAt}` into `Resolve-LifecycleStatus`. Foundation remains provider-blind and Operations remains discovery-blind.

## Current EKS model

The EKS root uses fixed defaults `cluster_name=platform-breakfix` and `aws_region=us-east-2`, an independent ignored local OpenTofu state, the AWS VPC and EKS modules, and an EBS CSI pod-identity module. It creates a VPC, two public subnets and routing/network resources, an EKS control plane, addons, one managed node group with two nodes/root volumes, EKS/IAM/security resources generated by the modules, and an EBS CSI IAM role/association. Optional ECR repositories share the root although preserved ECR is explicitly outside the ephemeral cluster lifecycle.

AWS provider default tags are:

```text
Project=platform-breakfix
ManagedBy=OpenTofu
Purpose=Disposable training lab
```

There is no pinned AWS account, unique lab-instance identifier, provider tag, profile identity, `CreatedAt` tag, `ExpiresAt` tag, TTL input, status metadata file, saved-plan metadata, or runtime lifecycle artifact. EKS has no breakfix profile framework. Current local state is ignored and contains only four preserved ECR repository/policy addresses; it contains no live cluster resources. This proves local state may outlive the cluster lifecycle and cannot by itself mean a lab exists.

Provision/destroy are direct `tofu apply`/`tofu destroy`. Connection assumes name/region and mutates kubeconfig. Validation calls `sts:GetCallerIdentity`, targeted `eks:DescribeCluster`, Kubernetes APIs, and EBS deletion checks. None is a status producer. There is no current command that reliably detects partial provision, partial destroy, or local/cloud disagreement.

## Ownership evidence and confidence

Ranked evidence:

1. **Future immutable instance identity on taggable primary and residual resources, combined with pinned account/region/provider identity — high confidence.** This does not exist today. It should include a random/immutable lab ID, `Project=platform-breakfix`, `Provider=eks`, stable creation/expiry facts, and explicit lifecycle ownership. The active AWS account must be compared with persisted expected identity.
2. **Exact cluster ARN plus all current project tags — medium confidence.** ARN binds partition/account/region/name and EKS returns tags with the cluster. Current configuration does not persist the expected account or unique instance ID, so an identically named/tagged lab in another selected account is plausible.
3. **Resource relationships from an owned EKS ARN/VPC — corroborating.** Node groups, subnets, security groups, IAM roles, and pod-identity associations can corroborate one owned graph but cannot establish initial ownership.
4. **OpenTofu state addresses/IDs — corroborating only.** State is local, can be lost or stale, and currently includes externally owned preserved ECR without cluster resources.
5. **Name `platform-breakfix` alone — unsafe.** It is configurable, not globally unique, and current scripts accept whichever AWS account the credential chain selects.
6. **Kubeconfig/context — unsafe for status.** It is mutable local connection state and contains credential execution configuration.

Current ownership confidence is insufficient for a public status producer. The three generic default tags identify repository purpose, not one immutable lab instance. Module-generated/secondary resources also cannot be assumed discoverable solely from provider default tags without characterization.

## NO_LAB semantics

`NO_LAB` requires positive absence, not a generic failed command. A future producer may emit neutral `NO_LAB` only when all are true:

1. AWS authentication succeeds and the active partition/account/region match the persisted expected ownership scope.
2. Targeted `DescribeCluster` for the exact expected name returns the specific EKS not-found condition, not AccessDenied, timeout, transport failure, or malformed output.
3. Bounded discovery across the explicitly owned lifecycle resource types proves zero resources with the exact immutable lab identity.
4. Local state has no cluster-lifecycle addresses that contradict cloud absence; explicitly preserved ECR addresses are classified separately.
5. No duplicate/conflicting ownership candidates or incomplete discovery page exists.

Current configuration cannot satisfy items 1 and 3 with high confidence. Cluster absence alone is not `NO_LAB`: VPC/IAM/security/node resources may remain after interrupted provision/destroy. A nonzero exit from `DescribeCluster` is never sufficient.

## ACTIVE semantics

Lifecycle `ACTIVE` means an owned lab primary exists, immutable `CreatedAt` and `ExpiresAt` are proven, and current time is before expiry. It is not Lab Health.

An owned EKS control plane may be the primary once identity metadata exists. Its Kubernetes/bootstrap/node/pod/addon health is irrelevant to lifecycle age. A control plane that exists with a missing node group or bootstrap may still represent an existing temporally active lab; provider phase and incompleteness should be retained as diagnostic facts outside the neutral contract. If ownership or temporal facts are incomplete, emit `INDETERMINATE`, not `ACTIVE`.

EKS service phase `ACTIVE` is not neutral lifecycle `ACTIVE`. The former is a control-plane service state; the latter is an owned lab's temporal state.

## STALE feasibility and temporal integrity

AWS EKS `cluster.createdAt` is the best current `CreatedAt` for a cluster-primary observation. It is AWS-authoritative, immutable for that cluster, and survives process restart, reclone, and local-state loss. It disappears with the cluster and cannot date a VPC-only partial provision or residual-only partial destroy. A future immutable creation tag applied at the lifecycle ownership boundary would cover those phases more consistently.

No reliable `ExpiresAt` exists. EKS has no four-hour TTL input/tag/output/runtime metadata. AKS advisory TTL is AKS behavior, not inherited EKS policy. Computing expiry as cluster creation plus the current AKS/default TTL would introduce new behavior; recomputing from mutable configuration could redefine an existing lab. OpenTofu state/file times and plan times are not authoritative.

Therefore meaningful EKS `ACTIVE`/`STALE` observations are currently blocked. `ExpiresAt` must be calculated once during the authorized lifecycle creation transaction and persisted as immutable cloud metadata alongside ownership identity. It must not be recalculated by status. If expiry metadata is missing from an otherwise proven owned lab, the producer should emit `INDETERMINATE` and foundation will return `UNKNOWN`.

Temporal facts must survive shell/process restart, terminal changes, checkout/reclone, and local runtime loss. Cloud tags do. Local state does not satisfy the latter two. During partial destroy, retained tagged resources must preserve the same facts until all owned resources are gone.

## INDETERMINATE and collection failure

`INDETERMINATE` is a valid observation only after collection succeeds and exact ownership is proven, but the complete lifecycle state cannot be classified. Examples include an owned residual-only resource graph, an owned cluster missing immutable expiry, a nonterminal/inconsistent partial graph, or proven cloud/local disagreement.

The following are collection failures, never successful `INDETERMINATE`/`UNKNOWN`: expired/missing authentication, wrong unverified account, AccessDenied, throttling without successful bounded completion, API/transport timeout, malformed JSON/shape, incomplete pagination, unsupported resource discovery, or ambiguous/duplicate ownership. Ambiguous ownership fails closed because selecting a candidate would guess.

Operations should eventually translate producer collection failure into the existing bounded unavailable error. M23 does not implement that mapping.

## Partial provision and destroy

| Condition | Provider-local conclusion | Neutral observation | Reason |
| --- | --- | --- | --- |
| Owned VPC exists; no EKS cluster | Partial provision | `INDETERMINATE` | Lab resources exist, so not `NO_LAB`; no cluster creation time/complete primary. |
| Owned EKS control plane exists; node group absent | Existing incomplete lab | `ACTIVE`/`STALE` only with immutable timestamps; otherwise `INDETERMINATE` | Node health/completeness is not lifecycle health, but ownership/time must be proven. |
| Owned cluster exists; bootstrap never ran | Existing lab | temporal `ACTIVE`/`STALE` when metadata is valid | Bootstrap/Kubernetes state is outside lifecycle status. |
| State contains cluster addresses; cloud primary absent | Cloud/local disagreement | `INDETERMINATE` after successful residual discovery | Never silently `NO_LAB`; destroy/recovery may still be required. |
| Cloud owned resources exist; local state missing | Orphaned cloud lab | temporal result if primary/metadata valid, otherwise `INDETERMINATE` | Cloud facts outrank missing local state. |
| Cluster deleted; owned network/IAM/security remains | Partial destroy | `INDETERMINATE` | Owned billable/privileged resources remain. |
| State remains after all cloud lifecycle resources are absent | Stale local state | `INDETERMINATE` | Status must expose disagreement; future repair/clean workflow decides resolution. |
| Only declared preserved ECR remains | No cluster lab if all positive-absence checks pass | `NO_LAB` | ECR is an explicit external exception and reported separately. |
| Generated AWS resource remains | Partial destroy | `INDETERMINATE` when exact ownership is proven; otherwise collection failure | Cannot claim clean absence. |

## Candidate read-only AWS discovery plan

No AWS command was executed in M23. A future producer would need bounded calls such as:

| API/CLI operation | Purpose and bounded data | Mutation | Failure handling | Pagination |
| --- | --- | --- | --- | --- |
| `sts get-caller-identity` | Partition/account/principal scope; expose account only | None | Auth/transport/malformed response is collection failure | None |
| `eks describe-cluster --name ... --region ...` | Exact ARN/name/status/createdAt/tags and VPC config | None | Only typed `ResourceNotFoundException` proves primary absence; all other errors fail | None |
| `eks list-nodegroups --cluster-name ...` | Corroborate expected compute/partial graph | None | Any incomplete/error result fails collection | Yes, `nextToken` |
| `eks describe-nodegroup` for returned exact names | ARN/status/createdAt/tags/resource relationships | None | Not-found may indicate partial graph; denial/timeout fails | None per node group |
| EC2 `describe-vpcs`, `describe-subnets`, `describe-security-groups` with exact immutable tag/ID filters | Detect owned network/residual graph | None | Unbounded/ambiguous/incomplete results fail | APIs may return `NextToken`; exhaust it |
| IAM `get-role` plus `list-role-tags` for exact persisted role names/ARNs | Detect owned roles without global role scans | None | Not-found is absence for that exact expected role; denial/timeout fails | `list-role-tags` may paginate |
| Resource Groups Tagging API `get-resources` with exact immutable tag and resource-type filters | Cross-check owned taggable residuals | None | Cannot be sole proof until coverage is characterized; incomplete result fails | Yes, pagination token |

`eks list-clusters`, unfiltered IAM role enumeration, and broad account-wide name scans are not proposed. Exact expected resource identities must first be persisted. A future implementation must characterize module-created resources and tag propagation; Tagging API coverage cannot be assumed for every generated resource.

## Status, health, and future verify-clean

Status answers owned lab existence and age. It does not require kubeconfig, Kubernetes API access, node readiness, workload rollout, storage, Cilium/Istio, dashboard, or scenario state. EKS service status and node-group facts may explain a partial graph but do not become Lab Health.

Status discovery can later support verify-clean by producing exact owned-resource inventory, primary-presence, residual-presence, ownership scope, and declared-exception facts. Verify-clean must additionally prove zero unintended leftovers and state cleanup; it remains unsupported and is not designed or implemented here.

## Contract compatibility and ownership

The existing foundation contract is structurally compatible: a future EKS adapter can emit exactly `State`, `CreatedAt`, and `ExpiresAt` without changing foundation. The current provider is nevertheless `BLOCKED_BY_TEMPORAL_METADATA` and `BLOCKED_BY_OWNERSHIP_DISCOVERY`. No contract mismatch exists.

| Responsibility | Owner |
| --- | --- |
| Validate/normalize neutral observation | `FOUNDATION` |
| AWS identity, exact resource discovery, ownership proof, partial-graph classification, observation construction | `EKS_PROVIDER` |
| Chosen advisory TTL duration/cost/operator policy | `BREAKFIX_POLICY` until independently extracted |
| Provider support, envelope, bounded error translation, presentation | `OPERATIONS` |
| Zero-leftover proof and exception report | `FUTURE_VERIFY_CLEAN` |

Security output is limited to account/region, non-secret ARNs/resource IDs, lifecycle tags, states, and timestamps. Credentials, tokens, principal session details, kubeconfig, certificates, endpoint credentials, state secrets, and raw diagnostic blobs must not enter the observation or Operations result.

## Recommended M24

Choose **B: first add missing immutable EKS lifecycle metadata**.

M24 should add only provider-native persisted metadata during EKS creation: a unique immutable lab identity, explicit project/provider/lifecycle ownership, expected account/region binding, one-time `CreatedAt`, and one-time `ExpiresAt` derived from an explicit EKS advisory TTL input. Apply the identity consistently to the taggable lifecycle resources and expose only non-secret values needed by a later producer. Characterize tag propagation and generated-resource identities. Keep preserved ECR explicitly external. Do not implement `get_lab_status`, Operations support, or verify-clean in the same milestone.

This is the smallest safe step because status discovery cannot truthfully identify one lab or classify `ACTIVE`/`STALE` until immutable cloud facts exist. Building the discovery primitive first would either trust mutable configuration/name, use broad ambiguous scans, or return only `UNKNOWN`. After metadata is live-proven stable through provision and partial destroy, a later milestone can implement bounded AWS discovery against it.
